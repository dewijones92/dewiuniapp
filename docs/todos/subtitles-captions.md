# Subtitles / captions

**Ask:** "lets also do subtitles/captions things."

## The unified seam (this one is a genuinely nice fit)

Captions on a video and a **transcript** on a podcast are the same thing: timed text
alongside the media. So one seam serves both pillars:

- `SubtitleTrack` in `:core:domain` — language code, label, url, format
  (VTT / SRT / JSON), `autoGenerated: Boolean`.
- `SubtitleSource` port in `:core:data` returning `List<SubtitleTrack>` for a
  `MediaItem`, with one adapter per pillar:
  - **Video:** yt-dlp's info dict already carries `subtitles` and
    `automatic_captions` (per language, with URLs and formats) — the bridge just
    needs to surface them, like it does formats today. Nothing new to fetch.
  - **Podcast:** Podcasting 2.0 `<podcast:transcript url= type=>` tags in the feed
    item — `RssParser` reads them (it already handles the `psc` chapter extensions,
    so the pattern is established).
- **Rendering happens once:** Media3 sideloads timed text via
  `MediaItem.SubtitleConfiguration`, so `Media3PlaybackController.play` attaches the
  chosen track and the existing player surface renders it — no per-pillar UI.

That means captions light up for videos *and* podcast transcripts from one
implementation, which is exactly what the Unified law asks for.

## Proposed shape

1. Bridge + parser expose the tracks (JVM-unit-testable against captured fixtures,
   like the other parsers).
2. `SubtitleSource` port + the two adapters, routed in `AppContainer` the same way
   `RoutedDownloadStrategy` routes downloads.
3. A CC button in the full player: Off / available languages, defaulting to the
   device locale when a matching track exists.
4. Remember the choice — per source, mirroring playback speed and (planned) volume
   boost.

## Open decisions

- **Auto-generated captions:** offer them (YouTube's ASR tracks are usually the only
  ones present), or only human-authored? Proposal: offer both, labelled
  "(auto)".
- **Downloaded media:** fetch the subtitle file alongside an offline download so
  captions work offline too? (Cheap — it's a small text file.) Proposal: yes, when
  a track is selected.
- **Podcast transcripts:** just render as captions (proposal), or also a scrollable,
  tappable transcript view (seek by tapping a line)? The latter is a bigger feature
  and would want a video equivalent to stay unified.
- Styling/accessibility: honour the system caption style
  (`CaptioningManager`) rather than inventing our own? Proposal: yes.

**Done when:** a video with captions and a podcast with a transcript both show timed
text through the one player, the language choice sticks, and it works offline for
downloaded items.
